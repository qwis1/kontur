# Отладка проекта «Контур»

## 1. Цель отладки

Отладка проводилась, чтобы убедиться, что все модули работают согласованно:

- браузер отправляет запрос по правильному адресу и методу;
- Flask принимает JSON и передаёт данные сервису;
- сервис и модель корректно проверяют значения;
- репозиторий выполняет SQL без ошибок;
- SQLite сохраняет и возвращает записи;
- frontend правильно отображает ответ и сообщения об ошибках.

## 2. Использованные инструменты

### 2.1. Режим Flask debug

Приложение запускается так:

```bash
python app.py
```

В `app.py` сервер запускается с `debug=True`. Это даёт:

- автоматическую перезагрузку после изменения файлов;
- подробную страницу ошибки с трассировкой стека;
- вывод исключений в консоль;
- интерактивный отладчик в браузере.

В тестах используется `TESTING=True`, чтобы ошибки приложения не скрывались
и тестовый клиент вёл себя предсказуемо.

### 2.2. Сообщения об ошибках

Проект возвращает понятные сообщения на русском языке. Например:

```json
{
    "error": "Недопустимый статус. Допустимые значения: Новая, В работе, Выполнена, Закрыта.",
    "details": [
        "Недопустимый статус. Допустимые значения: Новая, В работе, Выполнена, Закрыта."
    ]
}
```

Такие ответы позволили быстро отличать ошибку данных (400) от отсутствующей
заявки (404) и от ошибки метода (405).

### 2.3. Логирование

Постоянное логирование в учебном проекте не настраивалось: Flask сам выводит
в консоль запросы и необработанные исключения. При необходимости можно
добавить запись в журнал:

```python
app.logger.warning("Заявка %s не найдена", request_id)
```

Для текущего объёма данных достаточно консоли, страницы ошибки Flask
и вкладки Network. Это решение осознанное, а не отсутствующая часть.

### 2.4. Браузерные Developer Tools

Использовались вкладки:

| Вкладка | Что проверялось |
|---|---|
| Elements | структура карточек, классы статусов и приоритетов |
| Console | ошибки JavaScript, результат выражений, сетевые исключения |
| Network | URL, метод, заголовки, тело запроса и ответа, код состояния |
| Application | отсутствие лишних данных в Local Storage (проект их не использует) |

### 2.5. Проверка HTTP-запросов и JSON

В Network выбирался нужный запрос и проверялись:

- Request URL — совпадает ли с маршрутом Flask;
- Request Method — GET, POST, PUT, PATCH или DELETE;
- Status Code — 200, 201, 400, 404, 405 или 500;
- Request Headers — есть ли `Content-Type: application/json`;
- Request Payload — корректность JSON;
- Response — валидность JSON и наличие полей `id`, `status`, `error`.

Дополнительно те же запросы проверялись через Flask test client в pytest.

## 3. Порядок отладки

1. Воспроизвести проблему в браузере.
2. Открыть Network и найти неуспешный запрос.
3. Проверить URL и HTTP-метод.
4. Проверить тело запроса и заголовок `Content-Type`.
5. Проверить код и тело ответа.
6. Если ошибка на сервере — открыть трассировку Flask.
7. Если ошибка в данных — проверить валидацию и SQL.
8. Исправить код.
9. Повторить сценарий.
10. Добавить или обновить автоматический тест.
11. Запустить весь набор тестов.

## 4. Реалистичные проблемы и их решение

### Проблема 1. Неправильный URL API

**Симптом.** После нажатия «Создать заявку» появляется уведомление
«Маршрут API не найден», в Network запрос завершается кодом 404.
Форма очищается не всегда, список не обновляется.

**Причина.** В первой версии `app.js` использовался адрес `/api/request`
в единственном числе, а Blueprint зарегистрирован с префиксом
`/api/requests`.

**Способ обнаружения.** Вкладка Network показала:

```text
POST http://127.0.0.1:5000/api/request   404 (Not Found)
```

Ответ содержал JSON `{"error": "Маршрут API не найден."}`. Сравнение
с `url_prefix` в `routes/request_routes.py` выявило расхождение.

**Способ исправления.** Константа приведена к правильному значению:

```javascript
const API_URL = "/api/requests";
```

**Результат.** Запросы создания, получения, изменения и удаления начали
попадать в нужные маршруты. Ошибка больше не воспроизводится; адрес
зафиксирован в одном месте клиентского кода.

### Проблема 2. Неправильный HTTP-метод

**Симптом.** При смене статуса браузер получает 405, статус в карточке
возвращается к прежнему значению.

**Причина.** Для изменения статуса использовался метод POST на адрес
`/api/requests/<id>/status`, тогда как маршрут Flask принимает только PATCH.

**Способ обнаружения.** Network показал:

```text
POST /api/requests/1/status   405 Method Not Allowed
```

Ответ: `{"error": "Метод запроса не поддерживается для этого маршрута."}`.

**Способ исправления.** В `handleStatusChange()` метод заменён на PATCH:

```javascript
await apiRequest(`${API_URL}/${requestId}/status`, {
    method: "PATCH",
    body: JSON.stringify({ status: newStatus }),
});
```

**Результат.** Статус изменяется, `updated_at` обновляется, список
перерисовывается. Добавлен тест `test_update_request_status`.

### Проблема 3. Некорректный JSON

**Симптом.** При отправке запроса из стороннего клиента API возвращает 400
с сообщением «Некорректный JSON», хотя данные визуально выглядят правильно.

**Причина.** В запросе отсутствовал заголовок
`Content-Type: application/json`, либо тело содержало синтаксическую ошибку
(например, лишнюю запятую или незакрытую кавычку). Flask не мог разобрать
тело, `request.get_json(silent=True)` возвращал `None`.

**Способ обнаружения.** В Network вкладка Request Payload была пустой,
а в Headers отсутствовал `Content-Type`. Проверка тела через
`JSON.parse` во вкладке Console подтвердила синтаксическую ошибку.

**Способ исправления.** В клиенте тело формируется через `JSON.stringify`,
а `apiRequest()` автоматически добавляет заголовок при наличии тела.
На сервере добавлена явная проверка:

```python
data = request.get_json(silent=True)
if not isinstance(data, dict):
    return jsonify({"error": "Некорректный JSON. ..."}), 400
```

**Результат.** Некорректный JSON теперь даёт понятный ответ 400, а не 500
и не ошибку разбора на клиенте. Добавлен тест
`test_create_request_with_invalid_json`.

### Проблема 4. Ошибка в SQL-запросе

**Симптом.** При открытии списка сервер возвращает 500, в консоли Flask
появляется `sqlite3.OperationalError: no such table: request`.

**Причина.** На раннем этапе в одном из запросов было указано имя таблицы
`request` вместо `requests`. Таблица создавалась с именем `requests`,
поэтому SQLite не находила её.

**Способ обнаружения.** Трассировка Flask показала точный файл и строку
в `database/request_repository.py`. Запрос к `sqlite_master` подтвердил,
что существует только таблица `requests`.

**Способ исправления.** Имя таблицы приведено к `requests` во всех
SQL-запросах. Дополнительно SQL вынесен в один класс `RequestRepository`,
чтобы одинаковые имена использовались в одном месте.

**Результат.** Список и отдельные операции работают. Тесты API проходят
на чистой временной базе, где таблица создаётся заново.

### Проблема 5. Отсутствие обязательного поля

**Симптом.** Пользователь отправляет форму без категории, заявка не
создаётся. В интерфейсе появляется уведомление об ошибке, но поле
категории не подсвечивается.

**Причина.** В HTML у `select` было значение по умолчанию — первая реальная
категория, поэтому визуально поле всегда заполнено. При этом JavaScript
не проверял категорию перед отправкой, а сервер корректно возвращал 400.

**Способ обнаружения.** Network показал ответ 400 с текстом
«Необходимо указать категорию заявки». В запросе поле `category` было
пустой строкой.

**Способ исправления.**

- В форму добавлен пустой `option` с `selected disabled`.
- Перед отправкой JavaScript проверяет `payload.category`.
- При ошибке фокус переводится на нужное поле.
- Серверная валидация оставлена как обязательная защита.

**Результат.** Форма не отправляет заведомо неполные данные, а при обходе
клиентской проверки API всё равно возвращает понятную ошибку 400.
Добавлен тест `test_create_request_without_category`.

### Проблема 6. Неправильный статус заявки

**Симптом.** При попытке перевести заявку в статус «В работе » (с пробелом
в конце) сервер отвечает 400, хотя текст выглядит правильным.

**Причина.** Статус сравнивался со списком допустимых значений без
предварительной очистки строки. Пробел делал значение отличным от
`"В работе"`.

**Способ обнаружения.** В Request Payload был виден пробел в конце строки.
Ответ API содержал сообщение «Недопустимый статус...».

**Способ исправления.** В `RequestService.update_status()` значение
очищается методом `strip()` перед проверкой:

```python
if isinstance(status, str):
    clean_status = status.strip()
else:
    clean_status = ""
```

На клиенте статус выбирается из фиксированного списка `select`, поэтому
случайный текст ввести нельзя.

**Результат.** Корректные значения с лишними пробелами нормализуются,
недопустимые по-прежнему отклоняются. Добавлен тест
`test_update_request_with_invalid_status`.

## 5. Результаты отладки

### 5.1. Положительные результаты

- Приложение запускается командой `python app.py`.
- При первом запуске автоматически создаются папка `instance/`
  и файл `kontur.db` с таблицей `requests`.
- Главная страница открывается по адресу `http://127.0.0.1:5000`.
- Создание, чтение, редактирование, смена статуса и удаление работают
  через интерфейс и через API.
- Фильтры по статусу и категории возвращают корректные выборки.
- Русский текст в JSON отображается без escape-последовательностей.
- Ошибки API имеют единый JSON-формат и понятные сообщения.
- Все 25 автоматических тестов проходят на временной базе данных.

### 5.2. Обнаруженные ошибки

| № | Ошибка | Уровень | Код ответа |
|---|---|---|---|
| 1 | неверный URL `/api/request` | frontend | 404 |
| 2 | POST вместо PATCH для статуса | frontend | 405 |
| 3 | отсутствие `Content-Type` / битый JSON | frontend | 400 |
| 4 | имя таблицы `request` вместо `requests` | backend/SQL | 500 |
| 5 | пустая категория проходила клиентскую проверку | frontend | 400 |
| 6 | пробел в значении статуса | service | 400 |

### 5.3. Исправленные ошибки

Все шесть ошибок из таблицы исправлены:

- [x] URL приведён к `/api/requests`;
- [x] статус изменяется методом PATCH;
- [x] JSON формируется через `JSON.stringify`, заголовок добавляется
      автоматически, сервер проверяет тип тела;
- [x] имя таблицы исправлено во всех SQL-запросах;
- [x] добавлена клиентская проверка категории и пустой option;
- [x] статус нормализуется через `strip()`.

Для каждой ошибки добавлен или обновлён автоматический тест, чтобы
повторное появление было замечено при запуске `python -m pytest`.

## 6. Вывод

Отладка велась от внешнего признака к внутренней причине: сначала
фиксировался неуспешный HTTP-запрос в Network, затем проверялись маршрут,
сервис, модель и SQL. Такой порядок позволил быстро локализовать проблемы
и не менять работающие модули без необходимости. Итоговое приложение
запускается, а весь набор тестов проходит.
