# Инспектирование кода проекта «Контур»

## 1. Цель и порядок проверки

Инспектирование проводилось, чтобы убедиться, что код:

- соответствует PEP 8;
- использует единый стиль именования;
- понятен без длинных комментариев;
- не дублирует бизнес-логику;
- разделён по слоям ответственности;
- безопасно работает с базой данных;
- содержит docstrings для основных классов и функций;
- обеспечен тестами.

Порядок проверки:

1. просмотр структуры проекта и импортов;
2. проверка Python-файлов через `flake8`;
3. проверка синтаксиса JavaScript через `node --check`;
4. ручной просмотр моделей, сервиса, репозитория и маршрутов;
5. запуск `pytest`;
6. фиксация замечаний и исправлений.

## 4. Именование

| Элемент | Стиль | Примеры |
|---|---|---|
| модули и пакеты | snake_case | `request_service.py`, `request_routes.py` |
| функции и методы | snake_case | `create_request`, `update_status` |
| переменные | snake_case | `database_path`, `clean_category` |
| классы | PascalCase | `Request`, `ValidationError` |
| константы | UPPER_CASE | `ALLOWED_PRIORITIES`, `MAX_TITLE_LENGTH` |
| CSS-классы | kebab-case | `request-card`, `button-primary` |
| JS-функции | camelCase | `loadRequests`, `renderRequestCard` |
| JS-константы | UPPER_CASE | `API_URL`, `STATUSES` |

Имена отражают назначение: `not_found_response` формирует ответ 404,
`get_all_requests` возвращает список, `validation_error_response` —
ответ с ошибками валидации. Сокращений, требующих расшифровки, нет.

## 5. Разделение ответственности

| Слой | Файл | Что делает | Чего не делает |
|---|---|---|---|
| Представление | `templates/index.html`, CSS | разметка и оформление | не содержит SQL и бизнес-правил |
| Клиент | `static/js/app.js` | HTTP-запросы, DOM, уведомления | не проверяет данные вместо сервера |
| Маршруты | `routes/request_routes.py` | приём запроса, коды ответов | не содержит SQL и сложной логики |
| Сервис | `services/request_service.py` | валидация и правила | не зависит от Flask |
| Модель | `models/request.py` | структура и проверка заявки | не работает с базой напрямую |
| Репозиторий | `database/request_repository.py` | SQL CRUD | не формирует HTTP-ответы |
| База | `database/database.py` | подключение и схема | не знает о заявках как о бизнес-объектах |
| Конфигурация | `config.py`, `app.py` | сборка приложения | не содержит обработки конкретных заявок |

Ни один файл не выполняет одновременно рендеринг, маршрутизацию,
валидацию и SQL.

## 6. Дублирование логики

- Список допустимых приоритетов и статусов задан один раз в модели
  и используется сервисом и API.
- Преобразование строки БД в объект находится только в
  `Request.from_row()`.
- SQL-запросы собраны в `RequestRepository`, а не повторяются
  в каждом маршруте.
- Проверка статуса выполняется в сервисе; маршрут только обрабатывает
  исключение.
- Клиентские запросы проходят через одну функцию `apiRequest()`,
  поэтому обработка ошибок не дублируется в каждом обработчике.
- Отрисовка карточки вынесена в `renderRequestCard()`.

Небольшое дублирование есть в HTML: список категорий повторяется
в форме создания, фильтре и диалоге редактирования. Это данные
представления, а не бизнес-логика. При развитии проекта категории можно
получать из отдельного справочника API, но для текущего объёма такое
усложнение не требуется.

## 7. Docstrings и комментарии

Docstrings есть у:

- модулей (`"""REST API для работы с заявками."""`);
- классов (`Request`, `ValidationError`, `RequestService`,
  `RequestRepository`);
- публичных методов модели, сервиса и репозитория;
- функций маршрутов;
- вспомогательных функций JavaScript (`apiRequest`, `loadRequests`,
  `renderRequestCard`, `formatDate` и других).

Комментарии используются только там, где объясняют решение, а не
пересказывают код: настройка `ensure_ascii`, причина хранения сервиса
в `app.extensions`, назначение пустого option в форме.

## 8. Безопасность данных

### 8.1. SQL-инъекции

Все значения передаются параметрами:

```python
connection.execute(
    "SELECT * FROM requests WHERE status = ? AND category = ?",
    (status, category),
)
```

Название, описание и категория никогда не склеиваются с текстом SQL.
Динамически добавляются только фиксированные фрагменты
`"status = ?"` и `"category = ?"`, а не пользовательские строки.

### 8.2. XSS в интерфейсе

Пользовательские значения перед вставкой в `innerHTML` проходят через
`escapeHtml()`:

```javascript
return String(value ?? "").replace(/[&<>"']/g, ...);
```

Поэтому название вида `<script>alert(1)</script>` отобразится как текст,
а не выполнится.

### 8.3. Валидация на двух уровнях

Клиент проверяет обязательные поля для удобства, сервер проверяет их
повторно через `Request.validate()`. Обойти клиентскую проверку
через DevTools недостаточно: API вернёт 400.

### 8.4. Ограничения

Авторизации нет, поэтому любой пользователь с доступом к приложению может
изменять заявки. Для учебного проекта это допустимо. В реальной системе
потребовались бы аутентификация, роли и журнал действий.

## 9. Использованные подходы и шаблоны

| Подход | Где применяется | Что даёт |
|---|---|---|
| Service Layer | `services/request_service.py` | бизнес-правила отдельно от Flask и SQL |
| Repository-подобный слой | `database/request_repository.py` | SQL в одном месте, сервис не знает деталей БД |
| MVC-подобное разделение | `models`, `templates/static`, `routes` | представление, модель и управление разделены |
| Factory Function | `create_app()` в `app.py` | разные конфигурации для запуска и тестов |
| Blueprint | `routes/request_routes.py` | модульные маршруты с общим префиксом |
| Контекстный менеджер | `database_connection()` | гарантированное закрытие соединения |
| Фикстуры pytest | `tests/conftest.py` | изоляция тестов и переиспользование настройки |

Проект не использует ORM, Dependency Injection-контейнер, Singleton,
CQRS и другие шаблоны, которых в коде фактически нет.

## 10. Обработка ошибок

| Ситуация | Где обрабатывается | Ответ |
|---|---|---|
| пустое название | модель → сервис → маршрут | 400, русский текст |
| нет категории | модель → сервис → маршрут | 400 |
| неверный приоритет | модель → сервис → маршрут | 400 |
| неверный статус | модель/сервис → маршрут | 400 |
| заявка не найдена | сервис возвращает `None` → маршрут | 404 |
| некорректный JSON | маршрут | 400 |
| неподдерживаемый метод | обработчик приложения | 405, JSON для `/api/` |
| ошибка сети | `apiRequest()` на клиенте | уведомление пользователю |
| ошибка БД | Flask debug / трассировка | 500, исправляется при отладке |

Сообщения сформулированы так, чтобы пользователь понимал, что именно
нужно исправить.
