# Архитектура приложения «Контур»

## 1. Назначение приложения

«Контур» — внутреннее веб-приложение небольшой организации для регистрации
и обработки заявок сотрудников. Система помогает зафиксировать обращение,
назначить ему категорию и приоритет, а затем отслеживать статус выполнения.

Основные пользовательские операции:

- создание заявки;
- просмотр общего списка и отдельной заявки;
- редактирование данных;
- изменение статуса;
- фильтрация по статусу и категории;
- удаление заявки.

Приложение не является корпоративной системой: в нём намеренно нет
авторизации, ролей, сложной отчётности и интеграции с внешними сервисами.
Такая область позволяет сосредоточиться на интеграции программных модулей.

## 2. Общая схема

```text
Пользователь
    ↓
HTML-интерфейс (templates/index.html)
    ↓
JavaScript (static/js/app.js)
    ↓ HTTP / JSON / Fetch API
Flask Routes (routes/request_routes.py)
    ↓
Service Layer (services/request_service.py)
    ↓
Model (models/request.py)
RequestRepository (database/request_repository.py)
    ↓
SQLite (instance/kontur.db)
```

Стрелки показывают направление вызова. Ответ возвращается по той же цепочке
в обратном порядке: SQLite → репозиторий → сервис → Flask → JSON →
JavaScript → DOM.

## 3. Компоненты

| Компонент | Файлы | Ответственность |
|---|---|---|
| Пользовательский интерфейс | `templates/index.html`, `static/css/style.css` | разметка страницы, форма, фильтры, карточки заявок |
| Клиентская логика | `static/js/app.js` | Fetch-запросы, отрисовка данных, обработка ошибок, уведомления |
| Маршруты и REST API | `routes/request_routes.py` | приём HTTP-запросов, разбор JSON, коды ответов |
| Бизнес-логика | `services/request_service.py` | валидация, правила работы с заявками, фильтрация |
| Модель данных | `models/request.py` | поля заявки, допустимые значения, преобразование в словарь |
| Доступ к данным | `database/request_repository.py` | параметризованные SQL-запросы CRUD |
| База данных | `database/database.py`, `instance/kontur.db` | подключение, схема, хранение записей |
| Конфигурация | `config.py`, `app.py` | путь к БД, создание приложения, регистрация Blueprint |
| Тесты | `tests/` | проверка модели и REST API на временной БД |

### 3.1. Frontend

`templates/index.html` содержит:

- заголовок «Контур — система учёта заявок»;
- форму создания заявки;
- блок статистики;
- фильтры по статусу и категории;
- контейнер списка заявок;
- диалоговое окно редактирования;
- контейнер уведомлений.

`static/css/style.css` отвечает только за оформление. Внешние UI-фреймворки
не используются. Сетка адаптируется под ширину экрана.

`static/js/app.js`:

- хранит текущие фильтры и загруженные заявки;
- выполняет запросы через `fetch`;
- формирует карточки заявок;
- экранирует пользовательский текст перед вставкой в HTML;
- показывает успешные операции и ошибки;
- обрабатывает пустой список и состояние загрузки.

### 3.2. Backend

`app.py` реализует функцию `create_app()`. Она:

1. создаёт экземпляр Flask;
2. загружает настройки из `config.py`;
3. применяет тестовые настройки, если они переданы;
4. включает вывод русского текста в JSON без escape-последовательностей;
5. вызывает `init_db()` для создания базы и таблицы;
6. создаёт `RequestService` и сохраняет его в `app.extensions`;
7. регистрирует Blueprint с API;
8. добавляет маршрут главной страницы и обработчики ошибок 404/405.

Функция-фабрика позволяет тестам создавать независимые приложения
с временными файлами базы данных.

`routes/request_routes.py` содержит Blueprint `requests` с префиксом
`/api/requests`. Маршруты не содержат SQL и не выполняют бизнес-проверки:
они принимают данные, вызывают сервис и формируют HTTP-ответ.

`services/request_service.py` — слой бизнес-логики. Он не импортирует Flask,
поэтому может использоваться отдельно от веб-приложения. Сервис проверяет
данные, вызывает репозиторий и возвращает объекты `Request` либо `None`.

### 3.3. Слой данных

`database/request_repository.py` инкапсулирует SQL. Все запросы используют
параметры `?`, поэтому значения пользователя не подставляются в текст SQL.
Репозиторий преобразует строки `sqlite3.Row` в объекты `Request` через
`Request.from_row()`.

`database/database.py` отвечает за:

- создание подключения с `row_factory = sqlite3.Row`;
- гарантированное закрытие подключения через контекстный менеджер;
- создание папки `instance/`, если её нет;
- создание таблицы `requests` при первом запуске.

## 4. Модель данных

### 4.1. Таблица requests

```sql
CREATE TABLE IF NOT EXISTS requests (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    title TEXT NOT NULL,
    description TEXT NOT NULL DEFAULT '',
    category TEXT NOT NULL,
    priority TEXT NOT NULL,
    status TEXT NOT NULL DEFAULT 'Новая',
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL
);
```

| Поле | Тип | Назначение |
|---|---|---|
| `id` | INTEGER | уникальный идентификатор, назначается SQLite |
| `title` | TEXT | название заявки, обязательное |
| `description` | TEXT | подробное описание, может быть пустым |
| `category` | TEXT | категория, обязательная |
| `priority` | TEXT | приоритет из допустимого списка |
| `status` | TEXT | статус из допустимого списка |
| `created_at` | TEXT | дата и время создания |
| `updated_at` | TEXT | дата и время последнего изменения |

Даты хранятся в формате `ГГГГ-ММ-ДД ЧЧ:ММ:СС`. Такой формат удобно
читать в базе данных и несложно преобразовать в JavaScript.

### 4.2. Класс Request

Класс находится в `models/request.py`.

Поля объекта:

- `id`;
- `title`;
- `description`;
- `category`;
- `priority`;
- `status`;
- `created_at`;
- `updated_at`.

Публичные методы:

| Метод | Назначение |
|---|---|
| `Request(...)` | создание объекта и очистка строк от лишних пробелов |
| `validate()` | проверка обязательных полей и допустимых значений |
| `to_dict()` | преобразование объекта в словарь для JSON |
| `Request.from_row(row)` | создание объекта из строки SQLite |
| `__repr__()` | отладочное представление |

Константы модуля:

```python
ALLOWED_PRIORITIES = ("Низкий", "Средний", "Высокий")
ALLOWED_STATUSES = ("Новая", "В работе", "Выполнена", "Закрыта")
```

Правила валидации:

| Проверка | Результат при ошибке |
|---|---|
| название не пустое и не длиннее 120 символов | `ValidationError` |
| категория указана и не длиннее 80 символов | `ValidationError` |
| приоритет входит в `ALLOWED_PRIORITIES` | `ValidationError` |
| статус входит в `ALLOWED_STATUSES` | `ValidationError` |
| описание не длиннее 2000 символов | `ValidationError` |

`ValidationError` хранит список сообщений в атрибуте `errors`. API возвращает
первое сообщение в поле `error` и полный список в поле `details`.
Все сообщения сформулированы на русском языке.

Метод `to_dict()` возвращает все восемь полей. Именно этот словарь
сериализуется Flask в JSON.

## 5. Алгоритм создания заявки

```text
Начало
  ↓
Пользователь заполняет форму
  ↓
JavaScript проверяет название и категорию
  ↓
POST /api/requests с JSON-телом
  ↓
Flask получает JSON
  ↓
RequestService создаёт Request и выполняет validate()
  ↓
Данные корректны?
 ├─ Нет → HTTP 400 и список ошибок → уведомление в интерфейсе
 └─ Да → RequestRepository сохраняет запись в SQLite
  ↓
HTTP 201 и JSON созданной заявки
  ↓
JavaScript обновляет список и статистику
  ↓
Конец
```

На уровне кода цепочка выглядит так:

```text
handleCreateRequest() (app.js)
  → apiRequest(..., { method: "POST" })
  → create_request() (request_routes.py)
  → RequestService.create_request()
  → Request.validate()
  → RequestRepository.create()
  → INSERT INTO requests ...
  → jsonify(created_request.to_dict())
  → renderRequests() (app.js)
```

## 6. Изменение статуса

```text
Пользователь выбирает новый статус в карточке
  ↓
change → PATCH /api/requests/<id>/status
  ↓
Flask проверяет наличие JSON и поля status
  ↓
RequestService.update_status()
  ↓
Заявка существует?
 ├─ Нет → HTTP 404
 └─ Да → статус допустим?
         ├─ Нет → HTTP 400
         └─ Да → UPDATE requests SET status = ?, updated_at = ?
  ↓
JSON обновлённой заявки
  ↓
Список перезагружается с учётом фильтров
```

Если включён фильтр по статусу, после изменения заявка может исчезнуть
из текущей выборки. Это ожидаемое поведение: список всегда соответствует
выбранным условиям.

## 7. Обработка ошибок по уровням

| Уровень | Примеры ошибок | Способ обработки |
|---|---|---|
| Модель | пустое название, неверный приоритет | `ValidationError` с русским текстом |
| Сервис | недопустимый статус, отсутствующая заявка | исключение или `None` |
| Маршруты | некорректный JSON, отсутствие поля, 404 | JSON-ответ и правильный HTTP-код |
| Клиент | ошибка сети, ответ 400/404/500 | уведомление, возврат интерфейса в рабочее состояние |
| База данных | отсутствие файла или таблицы | автоматическое создание при запуске |

Единый формат ошибки API:

```json
{
    "error": "Понятное сообщение на русском языке.",
    "details": ["При необходимости — список уточнений."]
}
```

## 8. Архитектурные решения

1. **Функция-фабрика `create_app()`.** Позволяет запускать приложение
   с основной или временной базой и упрощает тестирование.
2. **Blueprint.** API отделено от главной страницы и может развиваться
   независимо.
3. **Service Layer.** Бизнес-правила находятся в одном месте и не зависят
   от Flask.
4. **Repository-подобный слой.** SQL собран в `RequestRepository`,
   а не разбросан по маршрутам.
5. **MVC-подобное разделение.** Модель, представление (HTML/CSS/JS)
   и управление (маршруты + сервис) разделены по папкам.
6. **Один объект подключения на операцию.** Для учебной нагрузки этого
   достаточно; соединения всегда закрываются контекстным менеджером.

Шаблоны, которых в проекте нет (например, полноценный ORM, DI-контейнер,
асинхронный сервер), намеренно не заявляются.

## 9. Ограничения архитектуры

- авторизация и роли отсутствуют;
- категории заданы в HTML, а не в справочнике БД;
- фильтрация выполняется только по двум полям;
- нет пагинации: при большом числе заявок список будет длинным;
- SQLite не рассчитана на большое число одновременных писателей.

Для целей учебного проекта выбранная архитектура достаточна: она
демонстрирует разделение ответственности, интеграцию модулей и позволяет
обоснованно расширять систему.
